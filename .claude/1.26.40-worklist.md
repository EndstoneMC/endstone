# BDS 1.26.40 adaptation - status

Branch `feat/26.40-support` off `v0.11`. Target release **1.26.40.8**.

This is a **major ABI break**, not a routine bump: 552 classes changed vtable shape, every byte
pattern had to be re-derived without symbols, and member layout shifted across at least 22 types
Endstone models.

## Reference material

- **No PDB ships for 1.26.40**, and the Linux ELF is stripped. Every symbol resolves by byte
  pattern, so nothing is name-verified.
- **No `bedrock-headers` for this release** (they stop at `android/r26_u3`). This ran as Scenario B
  throughout - everything below was derived from the binaries.
- IDA databases built with IDA 9.4 (the version `idalib` is bound to):
  `../bedrock-symbols/{win32_server_x64,linux_server_x64}/1.26.40/`.
  `win32_server_x64/1.26.32/bedrock_server.exe.i64` is the **named** reference (has PDB symbols).
- `bedrock-server-data` had not published 1.26.40 when this started; the tooling now falls back to
  Mojang's official download links.

## Done (committed, 16 commits, local only - not pushed)

### Symbol layer - complete
- **61/61 resolving on both platforms.** All 21 stale patterns relocated by anchoring on
  version-stable evidence (string literals, RTTI vtable slots, caller call-sequences), each
  confirmed against PE `.pdata` / ELF `.eh_frame` for function-start correctness.
- **Two silent-corruption bugs caught**, neither of which fails a build or a review:
  - `BatchedNetworkPeer::_receivePacket` resolved **2 bytes into** the right function (1.26.40 added
    a `push r15`). Hooking there skips the push while the epilogue still pops it - stack corruption
    on every received packet.
  - `getI18n` resolved to an **unrelated static**. Its pattern matches 18 byte-identical
    thread-safe-static singleton accessors that differ only in the rip displacement of the global
    they touch; the reshuffled link order moved a different one to the front. It passed `.pdata`,
    alignment *and* prologue checks - only call-closure marker strings caught it. Now anchored on
    the `"item.air.name"` SSO literal in `GiveCommand::execute`, which is unique binary-wide and
    resolves correctly in 1.26.32/36/40 alike.
- `dump_symbols.py` now **reports pattern ambiguity** (how many matches, how many distinct resolved
  addresses, which it took and which it rejected) instead of silently taking the first match.
  Entries still flagged ambiguous but verified correct: `registerOverloadInternal`,
  `symbolToString`, `DedicatedServer::start` (Windows) and five Linux entries.

### Protocol version
**1001 -> 2168.** Mojang **re-based** the numbering rather than incrementing. Confirmed five ways:
the `_validateLoginPacket` compare, a whole-image scan for the compare idiom, the RakNet MOTD
builder on both platforms, and `endweave`'s existing `protocols/v2168/` module. Anything assuming
small monotonic protocol steps needs review - DSL `since=` boundaries especially.

### Vtables - four classes, all matching the binary exactly
| Class | Change | Note |
|---|---|---|
| `BlockType` | 142 -> 133 | 10 scattered removals + 1 addition; also fixes the 8 block classes inheriting it |
| `Player` | 245 -> 246 | see drift note below |
| `Level` (`ILevel`) | 410 -> 412 (Linux) | inserts land in `ILevel`, not `Level` |
| `CommandOrigin` | 34 -> 35 | covers `VirtualCommandOrigin` by inheritance |

`Player` had **pre-existing local drift that cancelled in the total** - two virtuals missing around
slots 234/239, two tail declarations that actually belong to `ServerPlayer`. Slot counting alone
would have put the new virtual in the wrong place while the arithmetic still looked right.

Ruled out and needing no edit: gameplay handlers (BDS appends at the back, so the hard-coded
`vhook::create<N>` ordinals in `bedrock_hooks/server_instance.cpp` stay valid), `Block`/`Biome`
(the 22->23 belongs to `SubChunkStoragePaletted<T,...>`, not them), and everything past Endstone's
truncation markers.

### Signature changes - 3 of 4
| Function | Change |
|---|---|
| `Mob::knockback` | `int damage` -> `float damage`; arity and order otherwise identical |
| `Player::startSleepInBed` | gained `bool a2, float a3` |
| `ServerInstance::initializeServer` | `bool` -> `ServerInitialization::ServerInitResult`, a 32-byte struct returned indirectly |

`ServerInitResult` is modelled opaquely and deliberately left **trivially copyable** - destroying it
would release refcounts this layer does not own, at the cost of leaking two once per startup.

Because there is no PDB, a config `name` is **not BDS's real mangled name** - it is a lookup key
that must equal `__FUNCDNAME__` of Endstone's own declaration. So an ABI-correct declaration with
placeholder types is sufficient; only sizes, classes, order and return convention must be right.
Debt: if a future release ships a PDB, `--pdb` resolves by name and real type names start mattering
again - placeholder-typed declarations would silently fall back to pattern scanning rather than
erroring.

## Open

### 1. LIVE CRASH - `ServerInstance` member layout (highest priority)
```
ServerInstance::initializeServer   bedrock_hooks/server_instance.cpp:159
  -> getEventCoordinator()         bedrock/server/server_instance.cpp:34
     return event_coordinator_;    <-- access violation
```
`event_coordinator_` is a 24-byte `NotNullNonOwnerPtr`; copying it touches a control block, so a
wrong offset faults. `getEventCoordinator` is Endstone's own reimplementation reading the member at
Endstone's declared offset, so this is Endstone reading the wrong place.

**Ruled out:**
- Return-convention / corrupted `this` - line 155 passes `this` into the *real* `initializeServer`
  and survives; a bad `this` would have died there, not at 159.
- `Bedrock::Threading::Mutex` (immediately before it) - it is `using Mutex = std::mutex`, an STL
  type, stable across versions.
- The commented-out `profiling_manager` members - absent since 1.26.0.

**Still to determine:** the real displacement `getEventCoordinator` uses in 1.26.40 vs 1.26.36.
Note the size sweep reported `ServerInstance` 848 -> 880 with growth **at the tail** (+840..+872),
which alone would leave `event_coordinator_` unmoved - but that sweep reads sizes from the
destructor and so only sees **owned** members; a raw pointer or POD inserted mid-struct is invisible
to it.

`ServerInstance` has **no `BEDROCK_STATIC_ASSERT_SIZE`**, which is exactly why this surfaced as a
runtime crash instead of a compile error. Add one once the real size is known.

### 2. Member layout changes (no global signal - these surface one crash at a time)
Vtable changes had RTTI to make them findable in bulk. Member layout has no equivalent. All figures
below are **Linux only** - BDS's Windows build is `-fno-rtti` for Minecraft code, so there is no
name-anchored Windows size oracle. A CHANGED verdict transfers to Windows, but the **delta can
differ** (`unordered_map` 64/40, `std::string` 32/24). Windows sizes must be re-derived per class.

| Class | Linux size | Note |
|---|---|---|
| `DedicatedServer` | 400 -> 368 | diverges at the **first member**; Endstone reads `minecraft_`/`file_system_` |
| `ServerNetworkHandler` | 1824 -> 1808 | genuine reshuffle, not a shift; join path |
| `ConnectionRequest` / `SubClientConnectionRequest` | 48 -> 152 | structural rewrite; join path |
| `RakNetConnector` | 1432 -> 1896 | vtable also 24 -> 25 |
| `ServerInstance` | 848 -> 880 | see crash above |
| `Minecraft` | 544 -> 560 | first divergence +88 |
| `NetworkSystem` | 472 -> 480 | first divergence +144 |
| `ServerLevel` | 2304 -> 2312 | `Level` itself unchanged |
| `ResourcePackManager` | 400 -> 416 | |
| `ServerScriptManager` | 1088 -> 1112 | purely additive tail |
| `BlockActor` | 32 -> 40 | the one **asserted** class that changed; owned 8-byte member appended at +32 |
| `StartGamePacket` | -8 | |
| `TransferPacket` | +216 | |

Only 55 active `BEDROCK_STATIC_ASSERT_SIZE` assertions exist across ~655 headers, so this list is
not exhaustive. 20 asserted classes could not be measured at all - notably
`PlayerGameplayEvent<CoordinatorResult>` (a variant; drift there is a `bad_variant_access` crash)
and `Abilities`/`Ability` (a new `AbilitiesIndex` enumerator would add 12 bytes and silently shift
`Player`).

### 3. `CraftingDataPacket` - modelled, not yet applied
`prepareFromRecipes` no longer returns `unique_ptr<CraftingDataPacket>`; it returns
`CraftingDataPacketPayload` by value (0x110 = 272 bytes, `bool` at +0x108).
`sizeof(CraftingDataPacket)` 0x98 -> **0x148 = 328 on both platforms** =
`Packet`(48) + payload(272) @ +0x30 + `SerializationMode`(=5 `CerealOnly`) @ +0x140.

The single tagged `std::vector<CraftingDataEntry>` is replaced by **eleven per-kind vectors** of
flattened wire structs with no `Recipe` pointer. Decision taken: model the payload faithfully
(rather than rewriting `dumpRecipes` against `Recipes`, or stubbing it).

**Cross-validated against `bedrock-protocol/protocol/crafting.py`**, which already models
`@packet(id=52, since=2168)` with exactly those eleven lists plus `clear_recipes`. Two independent
derivations agree member-for-member; the binary's stride grouping matches the DSL's type
assignment, and Shaped = Shapeless + width + height explains the 8-byte delta.

Traps:
- **`NetworkItemInstanceDescriptorData` is not `NetworkItemInstanceDescriptor`.** The existing type
  derives from `ItemDescriptorCount` and is 64 bytes; the payload's is a flat non-polymorphic
  **48-byte** wire struct. Reusing it would be 16 bytes too big.
- **Furnace recipes are absent from the payload.** `dumpRecipes`' null-recipe `else` branch
  (`vanilla_data.cpp:267-283`) has nowhere to read. Absence is high confidence; the reason is not
  established, so do not delete that branch yet.
- Losses to accept in the dump: `priority` absent from Multi/SmithingTransform/SmithingTrim, `uuid`
  from both smithing types, `tag` from Multi. Item *name* is off the wire (numeric `id` only,
  recoverable via the existing `id_to_name` lambda); user-data NBT is already serialized, so the
  `NbtIo::writeNamedTag` step collapses to base64 directly. Ingredients survive unchanged.

Still open in the model: `SmithingTransform`'s internal offsets, four trivial element strides,
`NetworkItemInstanceDescriptorData`'s internal scalar order, `assume_symmetry` at +0x8C, and Linux
element-stride equivalence.

## Conventions used here

- **Never invent a Mojang name.** A shape ("returns a nested optional", "returns a null
  `unique_ptr`") proves the slot and the return kind, never the identity.
- Placeholder virtuals are `unknown<slot>`, unidentified members `unknown_<offset>_`, each with
  `// TODO(fixme): check the name` above and the observed fingerprint in a trailing comment.
  `grep -rn "TODO(fixme)" src/` is the back-fill list - **currently 12 entries**.
- **Guessed parameters are `a1`/`a2`/`a3`**, not descriptive invented names - `a2` is self-marking,
  `set_spawn_point` reads as verified when it is not. Names already in the tree stay.

## Verification status

- Build: **succeeds** (all 61 `consteval` symbol lookups resolve).
- Runtime: **fails at startup** - the `ServerInstance` crash above.
- `endstone_test /test` in-server is the authoritative check and has not passed yet. A vtable one
  slot off, or a member at the wrong offset, compiles and links cleanly - static verification cannot
  substitute for this.
